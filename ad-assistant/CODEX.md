# Codex 工作规则

Codex 在本项目中承担首席架构师、产品经理、安全负责人和代码审查员职责。

## 职责

Codex 负责：
- 架构设计
- 任务拆分
- 代码 Review
- 安全检查
- API 检查
- 数据库检查
- Provider 检查
- 成本检查
- 发布风险检查

Codex 默认优先 Review，不直接大规模改代码。

## 工作边界

Codex 不得在没有任务单的情况下写业务代码。

Codex 不得在没有用户确认的情况下开发：
- 当前任务单未写明的功能
- MVP_OPTIONAL 功能
- BACKLOG 功能
- FUTURE 功能
- BLOCKED 功能

## 重大变更流程

以下行为必须先输出方案，等待用户确认：
- 修改数据库表结构
- 修改 API 契约
- 修改 Provider 接口
- 修改授权逻辑
- 修改点数/算力系统
- 修改支付逻辑
- 修改登录逻辑
- 修改 Token 机制
- 修改项目目录结构
- 修改 shared DTO
- 修改 OpenAPI
- 修改 Tauri 权限配置
- 修改自动更新逻辑
- 引入新的第三方 SDK
- 升级核心依赖
- 删除文件
- 重命名目录
- 新增远程命令执行能力
- 修改文件系统权限
- 修改本地 Python 服务启动方式

重大变更方案必须包含：
1. 修改原因
2. 风险点
3. 影响范围
4. 回滚方案
5. 是否兼容旧版本
6. 是否需要数据库迁移

用户确认前禁止执行。

## Review 清单

每次 Review 必须检查：
- 是否只实现 `tasks/current-task.md`
- 是否存在前端直连第三方 AI API
- 是否泄露 API Key、Token、密钥、设备指纹
- 是否由客户端决定套餐、权限、扣点
- 是否所有 AI 调用经过 Provider 层
- 是否写入 `provider_call_log`
- 是否记录真实成本或可追溯估算成本
- 是否有云端授权校验
- 是否有请求限流和风控日志
- 是否修改了 API 契约、数据库、Provider 接口
- 是否新增依赖或升级核心依赖
- 是否修改 Tauri 权限、自动更新、本地服务启动方式
- 是否包含任务单验收标准要求的测试

## 提交闸门

每次提交前必须由 Codex Review。

Codex 必须在提交前输出：
- Review 对象
- 阻断问题
- 高风险问题
- 中低风险问题
- 测试覆盖
- 是否涉及重大变更
- 是否允许提交

只有当 Codex 明确给出“允许提交”时，才可以提交。

如果发现阻断问题、高风险安全问题、未确认重大变更或任务越界，必须拒绝提交。

## 模块交接规则

每个模块完成、Review 通过并合并到 `main` 后，Codex 必须准备下一次开发交接：

1. 根据 Sprint 计划和当前完成状态，更新或创建下一任务文档。
2. 明确下一任务的开发范围、禁止范围、允许文件、验收标准、测试方式、依赖权限和重大变更状态。
3. 明确建议的新分支名，例如 `feature/sprint-01-ocr-minimal`。
4. 提醒用户开启新会话，并在新会话开头提供项目路径、目标分支、任务文档和执行规则。

在下一任务文档准备完成前，不允许 Claude Code / DeepSeek 自行开始下一个模块。

## 输出格式

Review 输出必须按以下顺序：
1. 阻断问题
2. 高风险问题
3. 中低风险问题
4. 验收结论
5. 建议下一步

没有发现问题时，也必须说明剩余风险和未覆盖测试。
## Git Review And Commit Gate

Codex Review 必须检查 Git 提交流程是否合规：

- 当前实现是否在任务分支上，而不是 `main`。
- 分支名是否对应当前任务范围。
- 暂存文件是否只包含当前任务相关内容。
- 是否存在未确认的重大变更。
- 是否存在未通过 Review 仍尝试提交或推送的行为。
- 是否尝试直接推送 `main`。

Codex 只有在以下条件全部满足时，才能输出 `允许提交`：

1. 当前分支不是 `main`。
2. 阻断问题为 0。
3. 高风险安全问题为 0，或已经由用户明确确认接受。
4. 修改范围符合 `tasks/current-task.md`。
5. 测试或静态检查结果已经记录。
6. 提交目标明确为当前任务分支，推送目标明确为 `origin/<current-branch>`。

如果需要合并，Codex 只能建议通过 PR 合并到 `main`，不得建议直接 `git push origin main`。

# Codex 工作规则

Codex 在本项目中是任务单默认起草者和可选复核者。用户只给目标时，Codex 默认负责起草或更新 `tasks/current-task.md`；CC/DeepSeek 默认根据 Codex 编写或用户确认的任务单独立开发、测试、自审、提交任务分支和准备 PR。Codex Review 仍然是按需复核，不是每次提交的强制门禁。

## 工作边界

- 默认不主动继续项目任务。
- 只围绕用户明确指定的任务、commit、PR、diff 或问题开展工作。
- 默认只审查本次修改的文件、当前 diff、任务单和相关模块上下文。
- 不做全仓审查；只有当修改触及数据库、API、授权、Provider、点数、安全、CI、Tauri、依赖等高风险边界时，才读取必要的相邻文件。
- 未经用户确认，不执行会改变外部状态的 Git、Docker、数据库、CI、提交、推送或 PR 操作。

## 任务单与 CC 自主开发原则

- CC/DeepSeek 默认独立开发、测试、自审、提交到任务分支和准备 PR。
- Codex 默认负责起草或更新 `tasks/current-task.md`。
- CC/DeepSeek 不得自行扩大、重写或弱化 Codex/用户确认的任务单范围；任务单缺失、冲突或不可执行时，必须暂停并请求 Codex/用户更新。
- Codex Review 是可选复核，不是每次提交的强制条件。
- Codex 被召回时，只给出结论、风险和必要下一步，不扩展到无关范围。
- 如果 Codex 发现任务越界、高风险未确认、测试证据不足或 Git 流程不合规，直接指出并建议暂停。

## Codex 从无到有起草任务单规则

Codex 起草或更新 `tasks/current-task.md` 时，必须把用户目标写成 CC 可以直接照着执行的任务单。任务单不是方向说明，也不是一句“做某功能”；它必须手把手告诉 CC：为什么做、只做什么、不做什么、能改哪些文件、不能改哪些文件、怎么验收、怎么测试、什么时候必须停、怎么回滚。

### 第一步：先把用户目标翻译成明确任务

- 记录用户原始目标，保留关键业务意图。
- 先判断任务类型：新功能、Bug 修复、UI 调整、文档规则、测试补齐、重构、CI/环境任务或审查任务。
- 如果用户只给一句话，Codex 必须做保守拆解，把它变成一个最小可交付任务。
- 如果用户目标包含多个模块或多个阶段，当前任务只取一个闭环，其余写进“不开发什么”或后续任务。
- 如果目标和现有任务冲突，先说明冲突并要求用户确认，不能把互相矛盾的目标硬塞进同一张任务单。

### 第二步：读取足够上下文再写

- 先读 `README.md`、`CLAUDE.md`、`CODEX.md`、当前 `tasks/current-task.md`。
- 再读和任务相关的 `docs/*.md`、`docs/module-context/<module-or-task>/context.md`。
- 只读取与任务相关的代码或文档；除非触碰高风险边界，不做全仓审查。
- 如果当前任务是续做，确认上一任务状态、残余风险和未完成项。
- 如果工作区已有无关脏文件，任务单必须提醒 CC 不得混入提交。

### 第三步：写清楚任务目标和背景

- 写明任务名称。
- 写明为什么现在要做。
- 写明用户真正想得到的结果。
- 用一句话定义最终交付物。
- 明确这是当前任务，不是整个产品路线图。

### 第四步：写清楚本次只开发什么

- 用项目符号列出本次要做的内容。
- 每条都必须具体、可执行、可验收。
- 不写“优化一下”“完善一下”“处理一下”这类模糊描述。
- UI 任务必须写明页面、状态、布局、响应式要求和不可接受效果。
- 后端任务必须写明接口、服务、数据表、权限、错误码、事务和日志要求。
- 文档任务必须写明要改哪些规则、哪些旧口径必须清除。

### 第五步：写清楚本次不开发什么

- 明确列出 Out of Scope，防止 CC 顺手发挥。
- 后续再做的内容必须写成“不开发”，不能写成暗示 CC 可以顺手铺垫的描述。
- 默认禁止实现 BACKLOG、FUTURE、BLOCKED、真实支付、真实 AI 调用、云同步、未授权 Provider、未确认数据库变更。
- 如果任务只做前端壳，就明确不接后端、不改数据库、不接真实服务。

### 第六步：锁定允许文件和禁止文件

- `Allowed Files` 尽量精确到文件或目录。
- `Forbidden Files` 必须写出不能碰的区域，例如数据库、鉴权、支付、Provider、CI、依赖、Tauri 权限、生成物、日志、本地数据库。
- 如果允许新增文件，写清楚新增位置、命名规则和用途。
- 如果 CC 发现必须改 allowed files 之外的文件，任务单必须要求 CC 暂停并请求 Codex/用户更新任务单。

### 第七步：提前写明高风险和环境规则

- 明确是否涉及重大变更：是 / 否。
- 触碰数据库 schema/DDL/migration、API/OpenAPI/shared DTO、Auth/Token、Provider、credit/payment、Tauri 权限、依赖、CI、删除/清空用户数据时，必须写为高风险并要求用户确认。
- 本地启动服务和测试时，优先使用本机已安装应用，例如 PostgreSQL、Redis、缓存、OCR 服务等。
- 本机没有对应应用时，先安装本地应用；凡是需要安装到本机的桌面级应用，任务单必须要求安装到 `D:\APPLICATION`。
- 凡是需要安装到本机的环境依赖、SDK、CLI、运行时、模型、缓存、构建工具或其他外部工具，任务单必须要求安装或配置到 `D:\locaPath`。
- 任务单涉及安装、依赖下载或大缓存时，必须写明安装位置、缓存位置、是否会触碰 `C:` 盘；如果工具强制写入 `C:` 盘，必须要求 CC 先暂停并等待用户确认。
- 不得默认使用 Docker，除非 CI service container 或用户明确批准 Docker fallback。
- 新增或修改代码注释时，要求 CC 使用中文注释；第三方协议、外部 API 固定术语、错误码和英文专有名词除外。

### 第八步：把验收标准写到能直接检查

- 每条验收标准都必须能被人工或测试验证。
- 验收标准必须覆盖正常路径、失败路径、权限边界、空状态、重复操作和回归风险。
- UI 验收必须包含大窗口、小窗口、缩放、滚动条、视觉一致性等关键表现。
- 数据和安全任务必须包含数据一致性、权限校验、敏感信息不泄露、日志不落敏感内容。
- 不允许只写“功能正常”“页面美观”“测试通过”。

### 第九步：写清楚测试方法

- 写明必须运行的测试命令。
- 优先使用项目已有本地测试。
- 如果需要数据库、缓存或本地服务，写明本地服务要求和环境变量。
- 如果某类测试在当前环境无法运行，任务单必须要求 CC 说明原因、替代验证方式和残余风险。
- 禁止用“未运行测试”直接交付，除非任务单明确允许且说明理由。

### 第十步：写清楚交付、回滚和必须暂停的情况

- `Completion Output Required` 必须要求 CC 输出：修改文件、实现内容、未实现内容、测试命令和结果、风险、回滚方式、Git 状态。
- `Rollback Plan` 至少说明如何 revert commit、如何恢复配置、是否涉及数据回滚。
- 明确要求 CC 更新对应模块上下文和 `PROGRESS.md`。
- 明确说明任务单是执行规格，不是完成报告；CC 完成任务后只能对 `tasks/current-task.md` 做状态、分支、简短完成摘要、commit/PR 信息这类最小更新。
- 明确要求详细实现记录、测试结果、自审结论、reviewer-mode 结果和合并记录写入 `PROGRESS.md` 与对应模块上下文，不写入任务单正文顶部。
- 明确要求 CC 完成自审和 reviewer-mode 自查。
- 高风险任务必须写明：reviewer-mode 通过后还要请求 Codex 复核。
- 停机条件必须写清楚：任务单缺字段、范围冲突、需要改 forbidden files、测试失败且超出范围、发现 secrets、需要 Docker 但未获批准、需要删除/清空用户数据、需要真实支付或真实 AI 调用。

### 任务单最低字段

每个任务单至少包含：

- 任务名称
- 状态
- 背景
- 用户目标
- 本次只开发什么
- 本次不开发什么
- 允许修改哪些文件
- 禁止修改哪些文件
- 是否涉及重大变更
- 高风险边界
- 本地环境和服务规则
- 注释语言要求
- 验收标准
- 测试方式
- 安全检查
- 回滚方案
- 完成输出要求
- CC 必须暂停的情况

## 高风险边界

以下边界必须由 CC 先暂停并获得用户确认；Codex 被召回时重点复核这些边界：

| 边界 | 说明 |
|------|------|
| 数据库 schema / DDL / migration | 列类型、约束、索引、迁移脚本 |
| API contract / OpenAPI / shared DTO | 请求/响应结构、错误码、状态码语义 |
| Provider 接口 | Provider 基类、路由、模型选择、真实 Provider 调用 |
| Auth / Token | JWT 结构、刷新逻辑、权限模型、设备绑定 |
| Credit / Payment | 扣费逻辑、额度计算、定价、账本 |
| Tauri 权限 | 文件系统、网络、sidecar 声明 |
| 依赖变更 | `pyproject.toml`、`package.json`、lockfiles |
| 本地安装位置 | 桌面级应用默认安装到 `D:\APPLICATION`；环境依赖、SDK、CLI、运行时、模型、缓存和构建工具默认安装/配置到 `D:\locaPath`；强制写入 `C:` 盘需用户确认 |
| 本地 Python 服务启动方式 | sidecar 配置、CLI 调用路径、进程管理 |
| CI / 部署 | workflow、Dockerfile、环境变量约定 |
| 文件/目录破坏性变更 | 删除文件、重命名目录、大规模重构 |

## Review 规则

Codex Review 输出按以下顺序：

1. 阻断问题
2. 风险问题
3. 测试和证据
4. 验收结论
5. 下一步建议

结论使用：

- `复核通过`：未发现阻断问题，剩余风险可接受。
- `需要修复`：存在阻断问题或证据不足。
- `需要用户确认`：触碰高风险边界或范围不明确。

## Git 建议

- CC 可以在任务分支自审通过后提交和 push。
- CC 不直接 push `main`，不 force push；未经用户明确确认，不 self-merge。
- 用户明确确认某个 PR 可以合并后，CC 可以通过 GitHub PR 合并，并记录确认来源和合并结果。
- PR base 必须是 `main`，head 必须是当前任务分支。
- 高风险任务、失败测试、范围不确定或用户要求时，建议 PR 前召回 Codex 复核。

## 模块上下文

- 每个完成的模块都要更新 `docs/module-context/<module-or-task>/context.md`。
- 新任务开始前由 Codex 起草或更新当前任务单；CC 读取已确认任务单和对应模块上下文后再执行。
- Codex 被召回维护上下文时，只记录已验证事实、测试结果、风险和后续注意事项。

## 交流规则

- 需要给 Claude Code / DeepSeek 的下一步说明时，用中文，简短明确。
- 需要向用户汇报时，直接说明结论、风险和下一步，不扩展到无关范围。

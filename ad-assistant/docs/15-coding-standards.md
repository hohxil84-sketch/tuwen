# 15 编码规范

## 总原则

代码必须清晰、可审计、可回滚。

不得为了速度牺牲安全。

## 代码注释语言

CC 编写或修改代码时，新增注释必须使用中文。已有英文注释如需修改，也应改为中文，除非是第三方协议、外部 API 固定术语、错误码、英文专有名词或文件原有英文文档块的一部分。

新增函数必须添加简短中文注释，说明该函数的作用即可，不要求详细实现说明。注释用于解释业务意图、边界条件、风险或复杂逻辑，不要写“给变量赋值”这类无意义注释。

## TypeScript

要求：
- 开启严格类型检查
- 禁止使用 `any` 绕过类型，除非有注释说明
- API 类型来自 `shared/typescript`
- UI 组件不得包含 Provider Key、扣费逻辑、套餐最终判断

## Python

要求：
- 使用类型标注
- Provider 返回统一结构
- 错误码统一映射
- 日志必须脱敏
- 不得记录明文 Token、密码、API Key

## API

要求：
- 所有 API 返回统一响应结构
- 所有请求带 request_id 或由服务端生成 request_id
- 所有错误使用统一错误码
- 修改契约必须先确认

## 数据库

要求：
- 迁移脚本必须可回滚
- 扣费必须有流水
- Provider 调用必须有日志
- Token 只能存 hash 或加密值

## 可扩展性与可修改性

要求：
- 新功能必须接入现有分层，不绕开前端 `pages`、`stores`、`services`，也不绕开后端 `api`、`schemas`、`services`、`providers`、`models`
- 不硬编码未来会变化的业务规则；Provider、模型、套餐、价格、权限、限流、功能开关必须集中管理或预留配置入口
- API、OpenAPI、DTO、错误码和共享类型必须集中维护，禁止前后端各写一套互相漂移的结构
- 改动必须局部化、可回滚；不做无任务目标的大重构，不把多个模块混在一个任务里
- 同一业务规则出现两次以上时，优先抽到 service、helper 或集中配置，不复制复杂逻辑
- 核心边界通过明确接口扩展，包括 Provider、计费、权限、API 契约、Token 和设备绑定
- 每个完成模块的 `docs/module-context/<module-or-task>/context.md` 必须记录后续扩展入口、修改注意事项和已知限制
- `PROGRESS.md` 必须记录残余风险、后续修改入口和回滚方式，不只记录已完成内容

禁止：
- 为了快速实现把权限、扣费、Provider 路由或套餐判断散落到 UI、route handler 或临时脚本里
- 在没有任务单和回滚方案的情况下做跨模块重构
- 让前后端通过重复手写类型、错误码或响应结构来维持兼容

## 安全编码

禁止：
- 拼接未校验命令
- 拼接 SQL
- 明文保存凭据
- 前端保存 API Key
- 日志输出敏感字段
- 客户端决定权限和扣费
